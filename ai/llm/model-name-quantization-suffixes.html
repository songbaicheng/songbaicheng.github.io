模型名字里的 FP8、INT4、AWQ、GPTQ、GGUF 都是什么意思？

songbaicheng2026/10/12大约 14 分钟AI基础与原理AI大模型本地部署

下载本地模型时，同一个模型常有好几个版本：BF16、FP8、AWQ、GPTQ，还有一整排 Q4_K_M、Q5_K_M、Q8_0 的 GGUF 文件。

它们看起来都是后缀，却回答着不同的问题。FP8 说的是数值格式，AWQ 说的是量化方法，GGUF 说的是文件格式。把它们放在同一个排行榜里比较，类似于问“JPEG 和 1080p 哪个更好”，比较的层面就错了。

选版本的目的通常很具体：让模型在自己的机器上跑起来，留下足够的上下文空间，并且能接受它的回答质量。这篇围绕这个选择解释后缀，不讨论某个模型的实时跑分。

为什么同一个模型会有这么多版本

模型权重是大量数值。参数量相同，每个数值占的空间不同，完整权重的体积就不同。

假设一个模型有约 80 亿参数，全部以 16 位保存，单算数值需要约 16 GB；改成 8 位，理论上约 8 GB；改成 4 位，理论上约 4 GB。这里使用十进制 GB，也暂时忽略缩放系数等附加数据。

降低数值表示精度来减少空间的过程叫量化。量化并没有把 8B 模型变成 4B：参数数量通常不变，只是每个参数的表示更紧凑。它也不同于蒸馏，后者利用教师模型的信号训练学生模型。

代价在于数值不能完全还原。原本能区分的两个数，量化之后可能变成同一个近似值。量化方法要解决的，就是怎样在减少空间的同时控制这种误差。

接下来还有一个问题：这些数值怎样打包成文件，以及推理程序会不会读取和计算。于是一个模型名字里，可能同时出现参数量、训练版本、量化方法和文件格式。

FP16、BF16、FP8、INT4：数值怎样表示

FP16 和 BF16 都占 16 位，但并不相同

FP 是 Floating Point，浮点数。浮点格式把位数分配给符号、指数和有效数字，用有限的空间表示大小跨度很大的数。

FP16 和 BF16 都用 16 位，理论上每个数占 2 字节。BF16 把更多位分给指数，因此能表示的数值范围更大；FP16 则有更多有效数字位。在它们都能正常表示的范围内，FP16 的数值刻度通常更细。

因此，BF16 不是“比 FP16 多占显存的高级版本”，也不能简单叫它更精确。它们的空间相同，范围与精度分配不同。模型原本采用什么格式、硬件支持什么，才是选择依据。

FP32 是 32 位浮点数，每个数通常占 4 字节。这里的“精度”是数值表示精度，不是模型答题准确率；把权重转成 FP32 不会自动让模型多掌握知识。

FP8：8 位浮点，不是 INT8

FP8 是 8 位浮点格式的统称，常见变体有 E4M3 和 E5M2。E 表示指数位，M 表示尾数位，另有一位符号位。前者更偏向有效数字精度，后者提供更大的数值范围。NVIDIA 的 FP8 说明给出了这些格式的布局和用途。

FP8 和 INT8 虽然都是 8 位，却不是同一种表示。FP8 有浮点指数；INT8 是整数编码，量化方案通常还要配合缩放系数，把整数映射回近似的原始数值。

看到 某模型-FP8，可以知道它采用了 FP8 相关方案，却不能据此认定所有层、所有运算和缓存都采用 FP8。有的方案只处理权重，有的同时处理权重与激活，还可能按张量、通道或小块分别设置缩放系数。

硬件支持也要细看。支持读取 FP8 权重、能把它转换成另一种格式运行、拥有适配的原生 FP8 计算内核，是不同的能力。例如 Transformers 的 Fine-grained FP8 实现有自己的 GPU 要求，不能把这一要求当成所有 FP8 实现的统一门槛。

INT8 和 INT4：用整数编码近似权重

INT 是 Integer，整数。INT8 用 8 位，INT4 用 4 位。4 位只能提供 16 种编码，但模型权重并不只剩下全局统一的 16 个数值：不同分组可以有不同的缩放系数或零点。

一个简化的反量化关系是：

近似原值 =（整数编码 - 零点）× 缩放系数

具体方案可能采用对称量化，省略零点，也可能有更复杂的布局。这条公式只是说明：文件里保存的整数并不直接等于原来的权重。

INT4 的单个编码理论上占半个字节，通常把多个编码打包存储。加上缩放系数、零点和未量化的层之后，实际文件体积不会恰好等于“参数量 × 0.5 字节”。

AWQ 和 GPTQ：怎样把权重量化得更稳

同样压到 4 位，直接把每个数舍入到最近的刻度，并不一定能保住模型效果。不同权重造成的输出误差不同，量化方法会利用一些样本文本，观察模型计算时的表现，再决定怎样处理。这些用于观察的样本通常叫校准数据。

AWQ：参考激活，寻找更合适的权重缩放

AWQ 是 Activation-aware Weight Quantization，激活感知权重量化。激活是模型处理输入时产生的中间数值。

AWQ 利用激活信息识别对结果更敏感的权重通道，通过选择合适的缩放降低量化误差。名字里的 Activation-aware 表示“参考激活来处理权重”，并不表示激活本身一定量化成 4 位。

常见 AWQ 发布版本是 4 位权重，不过 AWQ 是方法名，不是“4 位”的同义词。作者的原始项目也介绍了 INT3/4 低位权重量化。下载时仍应检查模型配置中的 bits。

也不要把“保护重要权重”理解为“把某几个数原封不动存成 FP16”。AWQ 的核心做法包含缩放调整；实际文件中哪些层保留高精度，取决于具体实现。

GPTQ：减少量化造成的层输出误差

GPTQ 是另一种训练后权重量化方法。它利用校准数据和近似二阶信息，在量化一部分权重时调整其余权重，尽量降低层输出的重建误差。

这里的 GPTQ 不是“GPT 模型专属版本”，也不是另一款语言模型。不同模型架构可以采用这种方法，但推理程序仍需支持对应架构和量化实现。

GPTQ 同样不只由一个名字决定。位宽、分组大小、是否对称量化，以及保存布局都会影响兼容性。Transformers 的 GPTQ 文档就提醒了不同后端与旧检查点之间的兼容限制。

AWQ 与 GPTQ 不能脱离具体模型、校准数据和运行后端判断谁一定更好。一个版本在某张卡上更快，不代表换一张卡、换一种并发规模后仍然如此。

W4A16 和 W8A8：权重与激活分开写

W 是 Weight，权重；A 是 Activation，激活。

W4A16 通常表示权重采用 4 位、激活采用 16 位。常见 4 位 AWQ/GPTQ 部署采用类似组合，因此“4 位模型”往往只是权重压到了 4 位，计算过程中仍然有高精度数值。

W8A8 表示权重和激活都采用 8 位，但这个写法本身没有说明是 INT8 还是 FP8，也没有说明累加器、输出或 KV Cache 的精度。它是一条精度组合信息，不是整个推理流程的完整规格。

GGUF 和 Safetensors：文件怎样保存

GGUF 是文件格式，常见于 llama.cpp 及其相关应用。它可以保存权重和模型元数据，包括加载所需的架构、分词等信息。详细结构见 GGUF 格式规范。

GGUF 不等于 4 位量化。 同一个模型可以有 F16、BF16、Q8_0、Q4_K_M 等不同编码的 GGUF 文件。转换文件格式和降低数值精度也是两个步骤：先转换成高精度 GGUF，再量化成低位 GGUF，是一种常见流程。

Safetensors 也是保存张量的文件格式，Hugging Face 上很常见。它避免了 pickle 式权重反序列化的风险，并支持高效读取，但 .safetensors 后缀不说明模型有没有量化。BF16 权重和打包后的量化权重都可能保存在这种格式中。

一个 Safetensors 模型仓库通常还包含配置文件、分词器文件等。不能只复制一块权重文件就默认模型已经齐全；分片模型还需要完整分片及对应索引。文件格式的安全性也不意味着仓库中其他需要执行的自定义代码天然安全。

所以，AWQ 和 .safetensors 可以出现在同一个模型版本里：前者描述量化方法，后者描述存储方式，并不矛盾。

Q4_K_M、Q5_K_M、Q8_0：GGUF 文件里的具体量化规格

下载 GGUF 时，真正让人犹豫的通常是这一组文件名。

Q4_K_M 中，Q4 表示主要采用 4 位量化，K 表示 K-quants 分组量化家族，M 表示该预设的 Medium 变体。它会混合不同张量类型，部分权重使用更高位宽，因此整个文件的平均位宽通常高于 4 位。

M 不是“百万参数”，K 也不是“上下文 4K”。它们属于量化规格这一段，而不是参数量或上下文这一段。

Q5_K_M 是以 5 位为主的对应预设。Q6_K 是另一种 K-quants 规格。Q8_0 则是常见的 8 位分组量化格式；后面的 0 是格式标识，不是“没有质量损失”。

同一型号下的 S、M、L 常用来区分不同大小或混合策略，但不是每个量化家族都提供这三个版本。更细的 IQ 系列也有自己的编码与优化方式，不能仅靠数字推断文件大小或效果。

llama.cpp 的量化说明提供了一个 Llama-3.1-8B 示例：Q4_K_M 的平均位宽约为 4.89 bits/weight，文件约 4.58 GiB；Q8_0 约为 8.50 bits/weight，文件约 7.95 GiB。这是该文档中具体模型的结果，不是所有 8B 模型的固定体积，也不是本文的本机实测。

它说明了为什么“4 位模型”不一定严格按每参数半字节占空间。模型架构、保留高精度的张量和量化附加数据都会改变实际大小。

把完整名字拆开读

以下名称是教学示例，不代表某个实际发布仓库。

Example-32B-Instruct-AWQ

Example 是模型名，32B 是约 320 亿参数，Instruct 表示指令训练版本，AWQ 表示采用了 AWQ 量化。

这个名字没有告诉你全部信息。具体位宽和布局应查模型卡以及配置。例如下面是一个示意配置，不是所有 AWQ 仓库的固定值：

{
  "quantization_config": {
    "quant_method": "awq",
    "bits": 4,
    "group_size": 128,
    "zero_point": true,
    "version": "gemm"
  }
}

bits 才明确写出 4 位；group_size 是量化分组大小；version 在这类配置里描述实现布局，并非模型的训练代数。兼容性不能只核对 awq 这一项。

Example-8B-FP8

这个名字说明参数规模和 FP8 相关方案，但未说明训练版本，也未说明 FP8 应用于哪些部分。需要继续查模型卡、quantization_config 及运行后端要求。

不能因为它写着 FP8，就给不支持该实现的程序随便加一个参数强行加载。转换或回退路径是否存在，要看程序文档。

Example-8B-Instruct-Q4_K_M.gguf

Instruct 说明模型训练用途，Q4_K_M 说明量化预设，.gguf 说明文件格式。这三部分可以独立变化。

把 Base 模型量化成 Q4_K_M，不会自动变成 Instruct；把同一模型从 F16 压到 Q4_K_M，也不会改变它的参数量。还有一些名称写着 Coder、VL 或 Distill，分别可能涉及代码用途、多模态能力或蒸馏来源，应根据模型卡解释，不能当成量化标签。

如果文件名还有 00001-of-00003，通常是在说明它是三块分片中的第一块，不是三个任选其一的版本。下载时要确认所需分片齐全。

理论权重字节数 ≈ 参数数量 × 每参数位数 ÷ 8

以约 32B 参数为例，16 位约 64 GB，8 位约 32 GB，4 位约 16 GB。这只是统一位宽下的理论值，没有包含量化元数据与混合精度张量。

运行还需要额外空间：KV Cache 保存已有上下文的中间状态，计算需要临时缓冲区，框架也会预留或占用内存。上下文越长、并发越高，通常需要越多缓存空间。权重量化并不意味着 KV Cache 也自动采用相同位宽。

所以“16 GB 的文件”不能推出“16 GB 显存一定能跑”。反过来，有的程序可以将部分权重留在系统内存，或在多张卡之间分配，但速度、通信和后端支持会变成新的限制。多卡显存相加也不等于每个模型都能直接使用这块总容量。

下载时怎样选

先选运行程序，再选它明确支持的模型版本。顺序反过来，容易下载一个很小的文件，最后发现程序根本不会加载。

如果使用 llama.cpp 或基于它的应用，通常从 GGUF 版本入手，但仍需确认程序版本支持该模型架构和具体量化类型。内存有限、普通聊天用途，可以把 Q4_K_M 当成一个试用起点；有余量再比较 Q5_K_M、Q6_K 或 Q8_0。这个建议只是试用顺序，不承诺某个版本一定满足代码、数学或长文任务。

如果使用 vLLM、Transformers 等服务端框架，先查当前版本的量化支持表与硬件要求，再考虑 AWQ、GPTQ 或 FP8。框架支持某种量化方法，也未必支持这个模型架构、这个保存布局与这张 GPU 的组合。

如果希望尽量贴近原始发布版本的数值表现，而且内存足够，可以先用官方 BF16/FP16 版本作为比较基准。低位版本是否能接受，用自己的真实任务判断：代码能否执行、结构化输出是否合规、长文里的数字与限定条件有没有丢失。不能只问一句“你好”就认定量化没有影响。

速度也要实测。量化常能减少权重读取量，但反量化、缩放和不适配的内核可能抵消收益。处理长输入的速度与逐步生成的速度还可能表现不同，因此要分别观察首字等待时间、生成速度和实际显存占用，并在目标上下文与并发下测试。

最终需要核对的是：模型用途是否合适，程序能否加载，运行空间是否足够，以及回答质量和速度是否符合需求。后缀能帮助缩小选择范围，不能代替这几项检查。
